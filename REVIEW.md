# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | Startup & `create_employee` (lines 18–27, 79–83 in starter) | No database indexes created at startup, and TOCTOU check-then-insert race condition in `create_employee`. Without a unique index on `emp_code`, concurrent requests bypass `find_one` and insert duplicates. | Run 5 concurrent users via Postman Performance Test hitting `POST /employees` with identical `emp_code` — produces multiple 201 Created responses and duplicate documents in MongoDB. | Added `@app.on_event("startup")` creating idempotent indexes (`employees.emp_code` unique, `employees.department`, `attendance_logs(emp_code, date)` unique compound, `date`, and `status`). Removed redundant `find_one` check-then-insert and caught `DuplicateKeyError` on `insert_one` to return 409 Conflict atomically. |
| 2 | `compute_late_minutes` (lines 49–50 in starter) | Threshold check `minutes > 10` compares already-floored whole minutes instead of raw seconds. A punch-in strictly past grace period (e.g., 09:40:01 for a 09:30 shift) has `total_seconds = 601`, which floors to `minutes = 10`; because `10 > 10` is false, it returns `0` instead of `10`, granting an unintended 11-minute grace period and violating rule R2. | Call `compute_late_minutes(datetime(2026, 1, 1, 9, 40, 1), "09:30")` — expected `10` per rule R2, but starter returned `0`. | Computed raw elapsed seconds `total_seconds = (punch_in - start).total_seconds()` and checked `if total_seconds <= 600: return 0`, else `return int(total_seconds / 60)`. |
| 3 | `compute_late_minutes` (line 48 in starter) | Shift start is constructed via `punch_in.replace(hour, minute)` without timezone awareness. On UTC/cloud servers where `punch_in` is naive UTC, `start` is anchored to 09:30 UTC instead of 09:30 IST, skewing late calculations by 5 hours 30 minutes and marking late employees as early, violating rule R1. | On a UTC server, employee punches in at 10:00 IST (`04:30 UTC`) for a 09:30 shift — expected `30` late minutes, but `(04:30 - 09:30)` produced `-300` minutes (`0` late). | Ensured `punch_in` is localized/converted to IST (`punch_in.astimezone(IST)`) before deriving `start` per rule R1. |
| 4 | `compute_work_hours` (lines 53–54 in starter) | Uses Python's built-in `round()`, which applies IEEE 754 banker's rounding (round-half-to-even) and suffers from floating-point imprecision. When fractional hours hit midpoints with an even preceding digit (e.g., `8.045` or `7.545`), `round()` rounds down instead of up (`8.04` instead of `8.05`), undercounting work hours and violating rule R4. | Call `compute_work_hours(datetime(2026, 1, 1, 9, 0, 0), datetime(2026, 1, 1, 17, 2, 42))` (28,962 seconds = `8.045` hours) — expected `8.05` per rule R4, but starter returned `8.04`. | Used `Decimal` with `ROUND_HALF_UP` from Python's `decimal` module: `float((Decimal(str(total_seconds)) / Decimal(3600)).quantize(Decimal("0.01"), rounding=ROUND_HALF_UP))`, with `ensure_ist` normalizing both punch instants to IST per R1. |
| 5 | `compute_overtime` (line 60 in starter) | No 30-minute minimum threshold enforced. The function returns any positive difference between `punch_out` and `shift_end`, awarding overtime even for a few minutes. Rule R3 mandates that overtime is only counted when the difference is ≥ 30 minutes; otherwise it must return 0. | For shift ending at 18:30, employee punches out at 18:45 (15 min after shift) — expected `0` per rule R3, but starter returned `15`. | Computed elapsed minutes `minutes = int((punch_out - end).total_seconds() / 60)` and returned `minutes if minutes >= 30 else 0`. |
| 6 | `compute_overtime` (line 59 in starter) | `shift_end` is always anchored to `date_str` (the punch-in calendar day). For overnight shifts where `shift_end <= shift_start` (e.g., 22:00–06:00 per Rule R1), the shift ends on the **next** calendar day. Anchoring `end` to `date_str` sets `end` to 06:00 on the punch-in date (the previous day), miscalculating overtime by ~24 hours (1,440+ minutes). | Employee on 22:00–06:00 shift on 2026-01-05 punches out at 06:30 on 2026-01-06 — expected `30` min overtime, but starter computed `(2026-01-06 06:30 - 2026-01-05 06:00)` = `1470` minutes of overtime. | Added optional `shift_start` parameter and overnight detection: if `shift_end <= shift_start` (or `punch_out.date() > end.date()`), added `timedelta(days=1)` to `end`. Also normalized `punch_out` with `ensure_ist`. |
| 7 | `health` (lines 73–74 in starter) | Always returns `{"status": "ok"}` unconditionally without verifying database connectivity. If MongoDB is down or unreachable, the endpoint still returns 200 OK. The test suite/grader polls `/health` before running tests — if MongoDB is unreachable it wrongly gets a 200 and proceeds to execute tests against a broken database. | Stop or disconnect MongoDB (or configure unreachable `MONGO_URI`), then issue `GET /health` — starter still returns `200 OK` (`{"status": "ok"}`) instead of HTTP `503 Service Unavailable`. | Wrapped `client.admin.command("ping")` in a `try/except` block inside `health()`; caught exceptions and raised `HTTPException(status_code=503, detail="Database unavailable")` on failure. |
| 8 | `create_employee` (line 82 in starter) | `datetime.now()` produces a timezone-naive datetime in the host machine's local time. PyMongo serializes naive datetimes into BSON by treating them as UTC. On an IST server (UTC+05:30), `created_at` is stored 5 hours and 30 minutes ahead of the actual UTC instant, violating the contract that all instants must be stored as UTC in MongoDB. | On an IST machine, call `POST /employees` and inspect the inserted document in MongoDB: `created_at` is stored with the local clock time (e.g. `15:00:00Z` instead of `09:30:00Z`), 5h30m into the future. | Changed `datetime.now()` to `datetime.now(timezone.utc)` so the datetime is explicitly timezone-aware in UTC before BSON insertion. |
| 9 | `list_employees` (line 93 in starter) | Pagination off-by-one calculation: `skip = page * page_size`. For the default `page=1`, this skips 20 records (`1 * 20`), causing the first page to return records 21–40 and making records 1–20 permanently inaccessible. | Query `GET /employees?page=1&page_size=2` — returns employees 3 and 4 (`EMP0003`, `EMP0004`) instead of employees 1 and 2 (`EMP0001`, `EMP0002`). | Changed skip formula to 0-indexed offset: `skip = (page - 1) * page_size`. |
| 10 | `list_employees` (line 94 in starter) | `count_documents({})` unconditionally counts all documents in the collection using an empty filter, ignoring the `department` query filter. Rule R10 mandates that `total` must always reflect the applied filters. | Query `GET /employees?department=Engineering` when only 3 of 7 employees are in Engineering — response returns 3 items but reports `"total": 7`. | Passed the filter query dictionary `q` to `count_documents`: `total = db.employees.count_documents(q)`. |
| 11 | `list_employees` (line 95 in starter) | Missing `.sort()` on the database query. MongoDB returns documents in arbitrary physical insertion order, violating the OpenAPI contract which explicitly specifies results sorted by `emp_code` ascending. | Query `GET /employees` when documents are inserted out of order — records are returned in insertion order rather than sorted by `emp_code`, causing unstable pagination. | Added `.sort("emp_code", 1)` to the cursor before pagination. |
| 12 | `punch_in` (lines 102, 138 in starter) | Timezone-naive datetime and calendar date derivation. `datetime.fromtimestamp(ms/1000)` and `datetime.now()` produce naive datetimes in the local host timezone. On a UTC server, `ts.date()` evaluates to the UTC calendar date instead of the IST calendar date (e.g. 23:45 UTC is 05:15 IST the next day), violating Rule R1. Furthermore, for overnight shifts (`shift_end <= shift_start`), a punch-in before `shift_end` was not attributed to the previous calendar day's shift. | Send a punch-in at 23:45 UTC (05:15 IST next day) — attendance record date is stored as the UTC date rather than the IST calendar date. For an overnight shift employee (22:00–06:00) punching in at 01:00 IST, record date was set to current day rather than previous day. | Converted epoch ms instant to timezone-aware UTC datetime and localized to IST (`.astimezone(IST)`). Enforced Rule R1: if shift is overnight (`shift_end <= shift_start`) and punch-in time is earlier than `shift_end`, set `attendance_date` to `(dt_ist.date() - timedelta(days=1)).isoformat()`, else `dt_ist.date().isoformat()`. |
| 13 | `punch_in` (lines 102, 138 in starter) | Sub-second precision not truncated. Rule R1 explicitly mandates: "Instants are truncated to whole seconds before any calculation, and the truncated value is stored and returned." Starter left millisecond and microsecond fractions intact. | Send punch-in with timestamp having fractional seconds (e.g., `1783311000500`) — sub-second fractions cause incorrect floating/flooring computations in late minutes and store non-truncated instant in MongoDB. | Truncated microseconds to zero on instant conversion: `dt = dt.replace(microsecond=0)` before any calculation, database storage, or API response formatting. |
| 14 | `punch_in` (line 137 in starter) | Missing check for employee existence. If `emp_code` does not exist in `employees`, `db.employees.find_one(...)` returns `None`. The subsequent access `emp["shift_start"]` raises an unhandled `TypeError: 'NoneType' object is not subscriptable`, crashing the request with HTTP 500 instead of returning HTTP 404. | Send `POST /attendance/punch-in` with an unknown or non-existent `emp_code` — endpoint crashes with an unhandled HTTP 500 Internal Server Error instead of 404 Not Found. | Added check `if not emp: raise HTTPException(status_code=404, detail="Employee not found")`. |
| 15 | `punch_in` (lines 140–141 in starter) | TOCTOU check-then-insert race condition: `find_one` followed by `insert_one` is non-atomic. Two simultaneous punch-in requests for the same employee on the same date both pass the `find_one` check, leading to duplicate records or unhandled 500 errors. Contract mandates: "exactly one request gets 201 and the rest get 409." | Issue concurrent `POST /attendance/punch-in` requests for the same employee and date — both pass `find_one` check. | Removed non-atomic `find_one` pre-check; relied on the unique compound index `("emp_code", 1), ("date", 1)` and caught `DuplicateKeyError` on `insert_one` to raise `HTTPException(status_code=409, detail="already punched in for this date")`. |
| 16 | `PunchInIn` model (lines 66, 94–98 in starter) | Unrestricted string accepted for `status` and unvalidated `punched_at`. Starter used `status: str = "PRESENT"`, permitting invalid statuses like `ABSENT` or `LEAVE` (which per Data Model Section 3 and Rule R6 can only be created by back-office seed data or manual corrections) or arbitrary strings. In addition, seconds-looking integers (< 100000000000) were accepted. | Submit `POST /attendance/punch-in` with `{"status": "ABSENT"}` or `{"punched_at": 1783310280}` — starter accepts request with 201 Created instead of rejecting with 422 Unprocessable Entity. | Restricted status enum using `Literal["PRESENT", "WFH", "ON_DUTY"] = "PRESENT"` and constrained `punched_at: Optional[int] = Field(default=None, ge=100_000_000_000, le=4_102_444_800_000)` per `openapi.yaml`. |
| 17 | `punch_in` (lines 155–156 in starter) | Response shape contract violation and ID leakage. Starter explicitly added `doc["id"] = str(res.inserted_id)` and returned Python `datetime` objects. The assignment contract states: "`_id` is internal and never appears in a request or response. Attendance records have no id either." In addition, OpenAPI `AttendanceRecord` schema requires `punch_in` as an integer epoch milliseconds. | Automated schema validator inspects response of `POST /attendance/punch-in` — fails due to presence of unexpected `"id"` property and non-integer `punch_in` datetime string. | Removed `"id"` from the response, popped `_id`, and formatted response according to `AttendanceRecord` schema with `punch_in` as integer epoch milliseconds `int(dt_utc.timestamp() * 1000)`. |
| 18 | `list_attendance` (lines 144–146, 180–183 in starter) | Memory exhaustion, in-Python sorting and pagination, and missing compound secondary sort. `list(db.attendance_logs.find(q))` loads all matching documents from MongoDB into server RAM, sorts them in Python via lambda, and slices the page in memory. On a 100,000-record dataset, this takes multiple seconds, spikes memory usage by hundreds of megabytes, and causes out-of-memory crashes. Furthermore, the starter sorted only by `date` desc, missing the contract requirement: "Sorted by date descending, then emp_code ascending." | Benchmark `GET /attendance` against a 100,000-record database: the response takes seconds and consumes massive server RAM. Records on the same date are returned in non-deterministic order. | Pushed pagination and sorting entirely to MongoDB: used `total = db.attendance_logs.count_documents(q)`, created index on `[("date", -1), ("emp_code", 1)]`, and applied `.sort([("date", -1), ("emp_code", 1)]).skip(skip).limit(page_size)` on the cursor. |
| 19 | `list_attendance` (lines 148–150, 185–186 in starter) | Contract violations: exposing internal `_id` as `id`, returning BSON `datetime` objects instead of epoch milliseconds, omitting defaults for seeded records, missing `date_from > date_to` validation (422), and unbounded pagination parameters. Starter code performed `d["id"] = str(d.pop("_id"))`, exposing MongoDB ObjectIds. Instants (`punch_in`, `punch_out`, and `history.at` / `changes`) were returned as ISO strings. Seeded documents omitting `half_day` or `history` failed schema validation. | Query `GET /attendance?date_from=2026-07-08&date_to=2026-07-01` returns 200 with empty items instead of 422.
